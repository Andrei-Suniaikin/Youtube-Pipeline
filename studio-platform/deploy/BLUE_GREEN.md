# Выкатка без простоя («синий/зелёный»)

## Зачем

Сейчас `deploy/update.sh` делает `systemctl restart studio-platform`. Между «Stopping» и
«Application startup complete» проходит около 8 секунд (журнал 17.10: 17:27:53 → 17:28:01),
и всё это время студия не отвечает: минские пуллеры рендера и заливки, сборщик часов и
браузер ловят 502/500. 17.10 так было трижды за час.

Новая схема: два одинаковых экземпляра студии, `studio-platform@a` (порт 8001) и
`studio-platform@b` (порт 8002). Работает один; Caddy смотрит на него. Выкатка поднимает
новый код на **втором**, ждёт, пока он ответит на `/healthz`, переключает Caddy и только
потом вежливо гасит первый. Снаружи ни одного несостоявшегося запроса. Если новый не
поднялся — Caddy не трогается, старый работает дальше, код возвращается, как и раньше.

## Что при этом защищает фон

Несколько секунд (а если старый экземпляр как раз отдаёт ноде гигабайтный файл — минут)
с одной базой `vsgen.db` живут два процесса. Запросы они обслуживать могут оба. А фон —
нет: на старте каждое подприложение **возвращает «running»-задачи в очередь** (кабинет —
`_recover_orphans`, рерайт — `migrate_001(requeue_running=True)`, обложки —
`recover_interrupted_jobs`), и второй процесс без защиты переклеймил бы живые задачи
первого — двойной запуск за двойные деньги; движок выпусков в двух копиях дважды сделал
бы один шаг.

Защита — файловый замок `flock` на `/srv/studio/data/engine.lock`
(`shared/engine_lock.py`). Фон (движок выпусков, планировщик, пул воркеров, очереди
рерайта и обложек, возврат осиротевших задач) поднимает только тот процесс, который держит
замок. Второй отвечает на запросы и раз в 2 секунды пробует замок; как только первый
вышел — ядро отпускает замок, второй берёт его и поднимает фон с тем же возвратом
осиротевших задач, что и после обычного рестарта. Сигналов и ручного переключения нет.

Что это значит на практике:

* `/_instance` у любого экземпляра показывает `engine.state`: `owner` (фон здесь),
  `standby` (ждёт замок), `off` (замок не настроен — стенд).
* `/healthz` у запасного отвечает 200 с `scheduler.state = "standby"` — это не поломка.
* Воркеры картинок/озвучки, которых кабинет запускает подпроцессами, замок **не** уносят
  (файл открыт без наследования) и умирают вместе со своим экземпляром
  (`KillMode=control-group`), как и при обычном рестарте.
* Пока старый экземпляр дорабатывает начатые ответы, фон ведёт **он** (прежний код),
  новый ждёт. Простоя фона нет; есть задержка перехода, равная времени доработки.

Проверено тестом `tests/test_engine_lock.py`: два процесса, один `owner`, второй
`standby`; владелец вышел — второй забрал замок и сам поднял планировщик кабинета;
`/healthz` всё время 200.

## Что осталось как было

* Один каталог кода `/srv/studio/app`, один `git pull`, одна `.venv`, одна база.
* `/srv/studio/start-studio.sh` — тот же скрипт запуска у обоих экземпляров. Порт и имя
  экземпляр получает из `/srv/studio/instances/a.env` / `b.env` (файл читается **после**
  `studio.env`, поэтому `VS_PORT` оттуда выигрывает).
* `update.sh` без флага работает по-старому. Новая схема — только с `STUDIO_BLUE_GREEN=1`.
  После перехода запуск без флага **отказывается** работать (иначе он поднял бы третий
  процесс на 8090, на который Caddy не смотрит); настоять на старом режиме можно явно:
  `STUDIO_BLUE_GREEN=0`.
* Откат `--rollback`, ожидание заливок, `STUDIO_FORCE_RESTART=1`, обновление копии
  скрипта запуска, установка зависимостей — сохранены.
* Таймеры (`studio-alerts`, `studio-verify`, `studio-retention`, `studio-legacy-streams`)
  работают с базой напрямую и на порт не ходят — их схема не касается.

Чего больше **нет** в режиме синий/зелёный: ожидания «ноль идущих заливок» и файла
`upload-drain` перед выкаткой. Рвать нечего: новые запросы идут на новый экземпляр, а
старый дорабатывает начатые ответы (uvicorn при SIGTERM перестаёт принимать соединения
и ждёт конца текущих; `TimeoutStopSec=1800` в юните). Флаг «идёт выкатка» для рерайта
теперь отдельный файл `planned-restart` (ставится в обоих режимах, сам протухает за 30 мин).

## Установка (один раз, на VPS под root)

Порядок важен. Шаги 1–3 ничего не ломают и обратимы одной командой. Шаг 4 — момент
истины, но и он обратим.

### 0. Сначала обычная выкатка кода с замком

Код с замком должен работать **в старой одиночной службе** до перехода — иначе в шаге 3
два процесса поднимут фон одновременно. Эта выкатка — последняя с простоем в 8 секунд.

```bash
/srv/studio/app/deploy/update.sh              # обычный режим, как всегда
curl -s http://127.0.0.1:8090/_instance        # должно ответить JSON с "engine": {"state": "owner", ...}
```

Если `/_instance` отвечает 404 — код без замка, дальше не идти.

### 1. Файлы экземпляров

```bash
mkdir -p /srv/studio/instances
# в репозитории образцы лежат как *.env.example (.gitignore отсекает *.env — там обычно секреты;
# в этих файлах секретов нет, только порт и имя)
install -m 644 /srv/studio/app/deploy/instances/a.env.example /srv/studio/instances/a.env
install -m 644 /srv/studio/app/deploy/instances/b.env.example /srv/studio/instances/b.env
cat /srv/studio/instances/a.env /srv/studio/instances/b.env   # VS_PORT=8001 / 8002
ss -ltn | grep -E ':800[12] '                                  # порты должны быть свободны (пусто)
```

### 2. Шаблонный юнит

```bash
cp /srv/studio/app/deploy/studio-platform@.service /etc/systemd/system/
systemctl daemon-reload
systemctl cat studio-platform@a | head -5     # юнит виден
```

### 3. Поднять экземпляр «a» рядом со старой службой

```bash
systemctl start studio-platform@a
for i in $(seq 1 20); do curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8001/healthz && break; sleep 3; done
curl -s http://127.0.0.1:8001/_instance
```

Ожидается: `/healthz` → 200, в `/_instance` `"instance": "a"`, `"engine": {"state": "standby"`
— замок держит старая служба на 8090, и это правильно. Если `state` = `owner` — значит
старая служба запущена кодом без замка; вернуться к шагу 0.

### 4. Caddy: сниппет с активным портом

```bash
cp -p /etc/caddy/Caddyfile /etc/caddy/Caddyfile.bak.bluegreen-$(date +%Y%m%d-%H%M%S)
install -m 644 /srv/studio/app/deploy/caddy/studio-upstream.caddy /etc/caddy/studio-upstream.caddy
```

Теперь руками, в `/etc/caddy/Caddyfile` (образец — `deploy/caddy/Caddyfile.studio.example`):

1. первой строкой файла добавить `import /etc/caddy/studio-upstream.caddy`;
2. в блоке `studio.13.140.129.66.sslip.io { … }` заменить весь
   `reverse_proxy 127.0.0.1:8090 { transport http { … } }` на одну строку `import studio_backend`;
3. в блоке `vovastudio.work { … }` внутри `handle @studio { … }` — то же самое.

Проверить и применить:

```bash
caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
systemctl reload caddy
curl -s https://studio.13.140.129.66.sslip.io/_instance        # "instance": "a"
curl -s https://vovastudio.work/studio/ -o /dev/null -w '%{http_code}\n'   # 200 или 302 на вход
```

С этого момента весь внешний трафик идёт на экземпляр «a». Старая служба ещё работает и
ведёт фон.

### 5. Передать движок и убрать старую службу

```bash
systemctl stop studio-platform                 # вежливо: дорабатывает начатые ответы
sleep 5; curl -s http://127.0.0.1:8001/_instance   # "engine": {"state": "owner"
systemctl disable studio-platform
systemctl mask studio-platform                 # чтобы не подняли по привычке
echo a > /srv/studio/instances/active
systemctl enable studio-platform@a
journalctl -u studio-platform@a -n 20 --no-pager   # «замок наш, поднимаю фон», «фон запущен»
```

Единственный момент с простоем **фона** (не HTTP): между остановкой старой службы и
«замок наш» у «a» — около 2 секунд.

### 6. Проверка

```bash
STUDIO_BLUE_GREEN=1 /srv/studio/app/deploy/update.sh --status
```

Ожидается: `active-файл: a`, Caddy файл и живой — порт 8001, экземпляр a `active`,
движок `owner`, экземпляр b `inactive`, одиночная служба `inactive`/`masked`.

Чтобы не писать флаг каждый раз:

```bash
echo 'export STUDIO_BLUE_GREEN=1' >> /root/.bashrc
```

## Как теперь выкатывать

```bash
STUDIO_BLUE_GREEN=1 /srv/studio/app/deploy/update.sh            # до свежего в текущей ветке
STUDIO_BLUE_GREEN=1 /srv/studio/app/deploy/update.sh main       # конкретная ветка/метка
STUDIO_BLUE_GREEN=1 /srv/studio/app/deploy/update.sh --rollback # прошлая версия, тоже без простоя
STUDIO_BLUE_GREEN=1 /srv/studio/app/deploy/update.sh --status   # кто отвечает, у кого движок
```

Что делает скрипт по шагам:

1. сверяет три источника: файл `active`, работающий юнит, порт в `studio-upstream.caddy`.
   Расходятся — останавливается и говорит, что именно (руками не чинит и не гадает);
2. `git fetch` / `pull` (или checkout цели), обновляет копию `start-studio.sh`, ставит
   зависимости, если список изменился — как раньше;
3. запускает **запасной** экземпляр, ждёт `/healthz` → 200 до 60 с (20 попыток × 3 с);
   сверяет версию кода в `/_instance` и что движок у него `standby`;
4. переписывает порт в `/etc/caddy/studio-upstream.caddy` (атомарно), `caddy validate`,
   `systemctl reload --no-block caddy`, и ждёт до 30 с, пока в **живой** конфигурации
   Caddy (admin API на 127.0.0.1:2019) появится новый порт и исчезнет старый;
5. пишет новое имя в `active`, включает автозапуск нового, выключает старого;
6. `systemctl stop --no-block` старому и ждёт его выхода до `STUDIO_OLD_STOP_WAIT_SEC`
   (по умолчанию 900 с). Если старый всё ещё дорабатывает длинный ответ — скрипт выходит
   с объяснением: новый уже обслуживает всех, systemd добьёт старого сам, движок перейдёт
   автоматически. Проверить потом `--status`;
7. после выхода старого ждёт до 30 с, пока у нового `engine.state` станет `owner`.

Если шаг 3 или 4 не прошёл: журнал нового экземпляра на экран, новый останавливается,
код возвращается на прежний коммит (и копия скрипта запуска — из резервной копии),
Caddy и старый экземпляр не тронуты. Выход 1.

`STUDIO_FORCE_RESTART=1` в новом режиме означает: старого не ждать — `stop`, через 15 с
`SIGKILL`. Сорвёт идущую отдачу файла ноде, как и раньше.

## Откат

### Откат версии кода (обычный случай)

```bash
STUDIO_BLUE_GREEN=1 /srv/studio/app/deploy/update.sh --rollback
```

Та же процедура без простоя, только целевой коммит — из `/srv/studio/.previous-version`.
Как и раньше: откат возвращает **код, не базу** — если новая версия успела записать
статусы, которых старый код не понимает, проверить базу глазами.

### Выкатка «застряла»: Caddy переключён, старый не выходит

Это не авария — всё обслуживает новый. Посмотреть, что держит старого:

```bash
STUDIO_BLUE_GREEN=1 /srv/studio/app/deploy/update.sh --status
ss -tnp | grep -E ':800[12] ' | grep ESTAB          # живые соединения
systemctl kill -s SIGKILL studio-platform@<старый>  # если решили не ждать
```

### Полный возврат к одной службе на 8090

Если что-то пошло не так и нужна прежняя схема:

```bash
# 1. Caddy обратно на 8090
cp -p /etc/caddy/Caddyfile.bak.bluegreen-<дата> /etc/caddy/Caddyfile
caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile && systemctl reload caddy
# 2. старая служба
systemctl unmask studio-platform
systemctl enable --now studio-platform
curl -s http://127.0.0.1:8090/healthz
# 3. экземпляры прочь (замок перейдёт к старой службе сам, когда они выйдут)
systemctl disable --now studio-platform@a studio-platform@b
rm -f /srv/studio/instances/active
```

После `rm active` `update.sh` без флага снова работает по-старому.

## Ограничения и что знать

* **Один каталог кода.** Между `git pull` и остановкой старого экземпляра старый процесс
  читает с диска уже новые статические файлы и шаблоны. Так же было и раньше (между
  `pull` и `restart`), только теперь это окно — на время выкатки, обычно меньше минуты.
  Если когда-нибудь понадобится полная изоляция — два рабочих дерева git и
  `STUDIO_APP` на экземпляр; сейчас это не нужно.
* **Обе версии должны быть с замком.** `--rollback` на коммит без `shared/engine_lock.py`
  поднимет второй фон рядом с первым. После первой выкатки в новой схеме
  `.previous-version` всегда с замком; на коммиты старше — только через полный возврат
  к одной службе.
* **`caddy reload` может висеть**, пока старые соединения Caddy дорабатывают длинные
  ответы (Caddy по умолчанию ждёт их без ограничения). На переключение это не влияет:
  новая конфигурация уже применена, скрипт проверяет это по admin API, а не по выходу
  команды. Если admin API Caddy выключен (порт 2019 не слушает) — скрипт честно скажет,
  что переключение не подтвердилось, вернёт прежний файл и остановится, старый экземпляр
  продолжит работать.
* **Оба экземпляра на одной машине, одна `.venv`.** `pip install` при смене зависимостей
  идёт в общую `.venv` при работающем старом процессе — как и раньше при одиночной
  службе (он тоже работал во время установки).
* **Перезагрузка машины.** Автозапуск включён только у активного экземпляра
  (`systemctl enable` делает скрипт). Если включить оба, оба поднимутся, Caddy будет
  смотреть на активного, а движок возьмёт тот, кто первым взял замок — не обязательно
  активный. Работать будет, но путать будет; поэтому — один.
* **Что не проверялось на бою.** Всё здесь написано по снимку VPS от 17.10 (юнит, порты,
  Caddyfile, `caddy v2.11.4`, admin API на 2019) и проверено локально тестом замка и
  `bash -n`. Сам переход на VPS не выполнялся — он в руках владельца по шагам выше.
