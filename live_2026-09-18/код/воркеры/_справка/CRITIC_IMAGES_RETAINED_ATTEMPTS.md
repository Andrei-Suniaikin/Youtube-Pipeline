# Семь актуальных image recovery ошибок

Read-only свидетельство: `critic_images_journal_actual.json`, задания15042,15041,15037,15043–15046. Оплаченные запросы при проверке не выполнялись.

У проблемных операций текущий journal state=rejected, attempts=8, remote_id отсутствует. Для15042 имеется109 done и55 rejected;15041 —98/58;15037 —148/12. Остальные четыре задания остановились на единственной обязательной reference-операции. У done-операций ID уникальны. Pins released, source=server, family=googler. Это серверный пул, а не целевой личный пул владельца.

`Journal.intent()` сохраняет и ограничивает бюджет8. Время последних rejected-записей предшествует последнему queue.started: последующие перезапуски очереди повторно читали тот же журнал, не сбрасывали бюджет. Из кода `_journal_generation` следует: текущий rejected фиксируется после явного отклонения POST без принятого ID; accepted terminal failure имеет отдельный state=failed.

Однако история предыдущих семи исходов не хранится в текущей записи. Нельзя заключить, что все8 запросов отклонены, что все8 оплачены или что причина всех отказов — provider outage. Последние логи оставляют generic «v6 генерация не удалась». Проверка чисел401/403/429 отдельно показала совпадения с миллисекундами timestamp, а не HTTP статусами; эти ложные сигналы исключены.

Вывод: подтверждены конечный бюджет, сохранение текущего состояния и отсутствие его сброса при queue retry. Доказательств дефекта lease/identity либо дубля незавершённого accepted ID в этих семи случаях нет. Правильная эксплуатационная категория — recovery_required с явным разбором, а не автоматически external outage или internal error.
